# 001-14h: check each walk wave as it lands, and stop paying for shared history prefixes

The dated-facts and no-skip checks (`app/analysis/walk_checks.py`, `array_history_checks.py`,
`tree_history_checks.py`) must cover every history of the walked tree before the judgment model answers anything.
They have found two real walk faults so far (a future-sized collateral, 001-13f; a skipped levy-day response, 001-14e),
each after the walk had run for a day, and each voided the walk. They currently run only inside the pool's reduction
(`tree_parts.py`), after the whole walk and after the node union, because the reduction's masses need the frozen node
catalog. The checks do not: a history's question facts and decision order depend on its own steps, not on other
pieces.

Measured cost (task 001-14g, `var/diag/001-14g/report.md`, `rates.json`): narrow histories cost about 1.2 s of core
time each to check (p90 1.21 s for histories under 8 draws), broad ones about 20-45 ms per history-draw. The tree is
expected near 8 million histories, most of them narrow (about 9 draws a history in the earlier walk), so checking the
whole tree costs roughly 18 hours of 160 cores, after a walk that itself takes days. A wave of the walk (about 75,000
histories, 700,000 history-draws, every 20 minutes or so) would need some 34 four-core lines to check.

Two changes:
- Make the checks a stage of their own that runs on one walk wave's GitHub run (its `out-N`/`heavy-N` artifacts,
  laid out as the pool already reads them), sized and resumable as 001-14g's reduction lines are, and reports per
  wave: histories and history-draws checked, failures by kind with uncapped counts, and examples. The final pool then
  takes the checks' results instead of recomputing them, and must still show that every history in the tree was checked
  exactly once (the same range coverage the reduction uses); a history checked twice or never must fail the gate.
- Make a narrow history cheap. Histories in a piece share long prefixes (they are a tree's leaves); a check that
  replays each history from the review date repeats the shared work. Replay a piece's histories so each step's
  before-answer state is built once for all histories through it, keeping the checks independent of what the walk
  recorded. Aim for about 0.3 s of core time per narrow history or better, so that one wave's checks fit in about ten
  four-core lines of about 12 minutes.

Verdicts must not change: identical to the current checker on a few hundred real histories, narrow and wide; the saved
leaking fixture (`tests/fixtures/walk_f34_walk-f34-0002_168_judgment_response.json`), the levy-day regression
(`tests/test_same_day_frontier.py`) and planted faults still fail; cleared false alarms still pass. Real pieces:
`var/remote/walk-f34/heavy-0/` with manifests in `var/remote/walk-f34/out-0/`; the current walk's first wave
(walk-h1) will be on GitHub shortly. Put trial lines in `var/diag/001-14h/run.txt`; keep local runs to a few minutes.

Done: a check stage that runs on a walk run and reports per wave; the final gate takes its results with exact coverage;
the measured narrow-history cost and the projected lines per wave; identical verdicts as above.
