# 002-10: every question's key, record and class in the dated walk, checked against the Python walk

The product is moving to an exact evaluator (`design/002-exact-evaluator.md`; read it whole, especially "The dated
walk" and "The walk, compiled"): the whole tree of what can happen in the lawsuit, walked one operating draw at a time
in numba (`app/exact/tree.py`: `explore` is pass 1, `follow` drives one history of the Python walk through the same
code). Pass 1 must give the exact set of distinct questions the judgment model is asked: a question is its key (the
decision, its context, the path's amount class: `dispute_002:settlement_offer|I0|claimed`) and its situation class on
the draw (`#1130000200-2260000400.unpaid.current.listed.available.nopay.ctx.g2`). That count, with a cost estimate,
goes to Owen before any judge is run, so a key or class that is wrong or coarser than the Python's would ask the judge
the wrong questions or too few.

What exists (read each, and what it calls):
- `app/exact/tree.py`: the dated walk; each question asked emits a row (`fields_walk.Q*` columns: node, context, amount
  class, extra, option group, day); `tree.follow` collects each asked question's row, record and class.
- `app/exact/qrecord.py`: which record each question node reads (`record.record`, task 002-9) and its class
  (`record.situation_class`); its docstring lists what is missing.
- `app/exact/record.py`, `fields_record.py`, `decode.py` (task 002-9): the record's layout, the compiled reader, the
  decoder back to `question_row`'s dict, the class codes and their string; `var/record/report.md`: what 002-9 found.
- `app/exact/pass1.py`: `follow(..., questions=True)` returns each question asked, with `script_of` mapping a Python
  history's steps to the dated walk's elementary answers.
- The Python: `app/disputes/forecast.py` (`_Walk`'s constructors and `node`/`key` building, `situation_conditions`,
  `contexts`, `context_class`, `_context_tags`, `uses_appeal_status`, `uses_stay_status`, `question_class`,
  `group_classes`, `as_of`), `app/disputes/notes.py` (`record`, `decision_row`: the notes questions' records),
  `events.Chain.court_questions` and `_size_stay` (the court's stay question), and `oracle.histories`' paths:
  `DisputePath.edges` (each question's key and answer) and `DisputePath.classes` (each key's class on every draw).

Do:
1. **Keys.** A Python function rendering an emitted row (with the case's tables: `pass1.case_tables`) to the Python
   walk's key string(s): the verdict row to the verdict form's questions (`verdict_classes`' conjunction for the class
   taken), settlement to its offer and accept keys, the ruling with its remittitur, the notes origins
   (`judgment_I1`, ...), the response's `first`/`after_offer`/... and so on: exactly the keys the Python edges carry.
2. **Records of the elementary questions** (each at its own date in the dated walk): the court's answer to a stay
   motion (the Python's court question: `court_questions`/`_size_stay`, with its security terms), the registration
   orders, `petition_on_notes` and `holders_involuntary` (`notes.record`), `hearing_request`, `offering_closes`. Add
   their reads to `qrecord.question` (and to `record.py` where a field is missing).
3. **Classes.** The context tags in compiled form: per question node its conditions (`situation_conditions`), the bits
   held on the record's day, the motions and stay-status tags, with the path's amount class and context, so Python can
   render the exact `.ctx` suffix (`context_class`); and per node whether the class carries the appeal and stay status
   (`uses_appeal_status`, `uses_stay_status`). The class is integers in the walk; strings only in Python.

What must hold, on random histories of the Python walk (`oracle.histories`, both styles, several seeds, its draws),
each followed through `pass1.follow(..., questions=True)` on each of its draws: every key the Python path carries on
the draw is a key the dated walk asks there, and none extra, except the classes the dated walk's design explains
(the I3 settlement asked before a later stay approval; the merged listing answers); and for each key, the dated walk's
class on the draw equals `DisputePath.classes`' entry for the draw, and its decoded record equals the Python's record of
it (`as_of`), field by field. Where they differ, find why: report each difference by its cause with an example, and
where the Python reads a state other than the question's own date (design: "The dated walk"), keep the dated walk's
reading and say so; do not copy a later answer into a record or class. Then run pass 1 (`pass1.explore`) on draws 145
and 365 and report the number of distinct (key, class) pairs on each.

Keep to `app/exact/qrecord.py`, `record.py`, `fields_record.py`, `decode.py` and new files (a renderer module, tests);
do not change `tree.py`, `agenda.py`, `walk.py`, `pass1.py` or the other areas' modules (the coordinator is changing
them). If you need something from them (an extra column in the emitted row, a value at the question), say so in your
report with what and why.

Done: every question's key, record and class from the dated walk, identical to the Python walk's on the followed
histories or each difference explained by its cause, with the counts of what was checked and the two draws' distinct
question counts.
