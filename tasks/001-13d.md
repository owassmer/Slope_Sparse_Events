# 001-13d: make the GitHub pool run on real walk artifacts, at real size

Task 001-13c built pooling in stages for GitHub's runners (node discovery, node union, reduction into partials,
combine; `app/analysis/tree_parts.py`, `tree_pool_jobs.py`). Its tests use artifact layouts it constructed. Run on a
real walk wave (walk-f34, GitHub run 38195968528, 40 artifacts), every line of the first stage failed at once:
`38195968528/heavy-0: events and piece.json directories do not match`.

How a walk line's outputs are really stored (see `.github/workflows/run.yml`, upload steps):
- `out-N` uploads `out/`, `var/diag/` and `var/walk-population/**/*.{json,txt}` together, so inside the artifact a
  piece's manifest is at `var/walk-population/walk-f34-0001/piece.json` (beside `out/log.txt`).
- `heavy-N` uploads only `var/walk-population/**/*.pkl*`, so its root is the walk-population folder and the same
  piece's events are at `walk-f34-0001/events.pkl.gz`.
The artifacts of walk-f34 and every other GitHub wave are already uploaded in this form and cannot be re-uploaded;
pooling must read them as they are. Pair each piece's events with its manifest by the piece's own folder, and keep
every existing check (a piece without its events, events without a piece, a duplicate, a truncated stream, counts that
disagree with `piece.json`) stopping the pool. A test must build its artifacts in exactly the layout above.

Where a pool line's own outputs go matters the same way. A line keeps only what matches the upload paths; `out-N`
comes back to the coordinator's 8 GB Mac and must stay small, `heavy-N` stays on GitHub. Owen is being asked to add
`var/pool/` to the `heavy-N` upload; write each part's partial under `var/pool/` and anything the coordinator needs to
read (timings, counts, the gate verdicts) under `var/diag/`. Do not change the workflow yourself.

Size the stages for the real limits rather than one artifact per line: a GitHub run takes at most 256 lines; each line
is a 4-core runner with about 16 GB memory and 86 GB free disk, and must finish within 20 minutes; 40 run at once.
The whole tree is expected near 8 million histories in about 6,000 pieces (about 110 GB of events, 1,500 GitHub
artifacts plus about 1,660 whole pieces to arrive later as local folders). 001-13c's own projection was about 34 GB of
partials and a single combine of about 30 minutes, over the limit; combine in levels if one line cannot hold it, and
make partials no larger than the gates need. Report the projected lines, runs and wall time per stage for the whole
tree from your measurements.

The coordinator will run the stages on walk-f34 as soon as you finish; generate their run.txt files from
`tree_pool_jobs` so they can be submitted one after another with the previous stage's run ID.

Done: the stage generator produces run.txt files whose lines work on artifacts laid out as above (shown by a test in
that layout); stage outputs are written where the workflow keeps them; the sizing for 8 million histories fits the
limits on paper from measured rates.
