# 001-13c: pool the walk on GitHub's runners, in parts

The full-tree walk will end with something like 8 million joint histories (an estimate that has undershot before), in
roughly 6,000 pieces over 40 or more waves, about 110 GB of events. Pooling (`slope pool-tree`,
`app/analysis/tree_pool.py`) turns those pieces into what the outcome's gates judge: coverage (every route walked exactly
once, judged by input routes), probability (on each of the 512 draws the histories' probabilities sum to 1 under any
answers), offered answers (every answer a history takes is one its question offers on that date) and dated facts
(every question's facts as they stood before its own answer), plus the question catalog and the saved sample that the
independent replay later reads. Nothing after it can start until it is done.

Task 001-13b made pooling read GitHub's split artifacts (`out-N` with `piece.json`, `heavy-N` with the events) and local
folders of whole pieces, and split ingestion and export over many processes, for a single 128-core host building one
SQLite database of about 173 GB. That host is no longer available: there is no budget for it. Pooling has to run on
GitHub's runners instead, through `run.txt` lines (see `scripts/remote` and `.github/workflows/run.yml`). A line is one
job on a 4-core runner with about 16 GB of memory and about 86 GB of free disk; up to 40 run at once; each command must
finish within 20 minutes and write its results as it goes. No single machine ever holds the whole tree.

So pooling must work in parts: each line takes a bounded set of pieces (by run and artifact, or by local folder),
checks and summarises them, and uploads a small partial result; a final step combines the partials into the same gate
verdicts, masses, catalog and sample a single pool of the same pieces would give. Everything the gates sum or join
must combine exactly: per-draw masses add, reach masks OR, questions union with the same domain check as now, coverage
works from every piece's input and remaining routes. What must not weaken: a duplicate piece anywhere (including in two
different parts) still stops the pool; a truncated piece or one whose histories or draws do not match its `piece.json`
still stops it; a route covered twice or never still fails coverage. The saved replay sample must be uniform over all
histories, not over parts. The partials must also be small enough that combining them fits one line.

After the judgment model answers, the cash distribution will need another pass over every history with those answers;
keep the parts so that pass can reuse them, but do not build it.

Some pieces (about 30 GB, from waves f7-f19) exist only in an S3 bucket that GitHub runners cannot read; how they
arrive is a separate question. Your design must accept them later as local folders of whole pieces, the same as now.

Measure on real pieces: `var/remote/walk-f*/` holds every GitHub wave's small files; the run IDs are in
`.runs/remote-walk-f*.log`. Put any real-size trial in `run.txt` and report what it showed.

Done: a `run.txt` pools a set of GitHub walk runs in parts within the limits above and a combine line gives the gate
verdicts; a test shows that pooling the same pieces in several parts and combining gives exactly what one pool gives,
and that a piece duplicated across two parts is caught. Report measured time per piece and per history, the number of
lines and wall time projected for 8 million histories, and the partials' total size.
