# 001-1j A stay's security is computed from the state, never re-sized on triggers

Four of today's engine defects were one: a stay's security is a derived quantity, cached on the chain and re-sized
only when hand-maintained triggers fire (`Chain.restay`, `_stay_key`). Each route that changed its inputs without a
trigger left a stale lock: waiting answers booked by `until` (001-1f), an offering closing before the approval
(other5), a queued levy or waiting decision (none279's skipped day-112 settlement), and draw 145's old day-161
cash-out. The next route would be the fifth.

Remove the class rather than add a trigger: the security, and anything read from it (the lock, its release, the
available cash and the dated triggers that depend on it), is computed from the chain's state when read, by the
stay-sizing rule as it stands (sized on its approval day, on the balance after every event dated before it, never
above that balance, never on or after a petition). Nothing remembers a size that its inputs can make stale.
`restay`, `_stay_key` and the trigger calls go. If something else on `Chain` is cached the same way, name it in the
result; don't change it here.

The tests that pin those four cases must pass unchanged in meaning, and so must the no-skip check
(`tests/walk_order.py`) on one root locally. Put the full set of roots and the focused tests in `run.txt`, commit,
and stop; the coordinator runs them on GitHub. Report the walk's time on the local root before and after. No cloud
and no judgment calls.

Do not run the full test suite here: this Mac is short of memory and the suite takes over 30 minutes. Run the tests for what you change; the full suite goes in `run.txt` with the roots.
