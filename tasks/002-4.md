# 002-4: the cash analysis in one pass

Outcome 002 (`outcomes/002.md`): on a fresh clone, one command runs the Akoustis 14 May case and serves its page in
under an hour on a laptop, with every expected figure's range no wider than 1% of the commitment. The range narrows
only with more sampled histories, so the time per history decides how narrow the page can be within the hour. Today
the cash analysis (`Analysis` in `app/analysis/core.py`) goes over every history twice: a first pass computes each
history's event cash to fix the histogram bins' ranges (`_bins`, `_event_range`), keeping some of it packed, and a
second pass computes the event cash again where it was not kept, runs the engine (`run_many`) and reduces
(`Reduction.add`). On the answer-first run of 1,331 histories (stand-in judge, 512 draws) each pass took about 6 1/2
minutes on this Mac when it was quiet; together they are about half of the run.

Make the analysis cost one pass: each history's event cash computed once and the engine run once. How is yours to
decide: the bins' ranges could come from bounds that hold for every history (the line's own limits give such bounds;
`app/analysis/stress_search.py` derives one for what is owed), or the reduction could keep what it needs and bin at the
end, or something else. What must not change is what the page shows: every figure, series and percentile the payload
carries must come out as before on the same histories, or where binning changes a percentile, by no more than the
bins' own resolution, which you state. Show it on the real case by comparing the payload's figures from both ways on
the same histories.

Measure on GitHub's runners, not this Mac (it is shared and its timings mean little when other sessions run): put
lines in `var/diag/002-4/run.txt` (each line has 20 minutes; `uv run slope run akoustis_20240514 --tau 0.05
--replicates 2` is a quick real build, and `--tau 0.01 --replicates 4` a fuller one), and report the analysis time
per history before and after, from the run's own log lines (`analysis bins`, `analysis simulate`). The coordinator
runs your lines and returns their output only if you ask for it in your report, so make each line print what you
need. Another worker may be changing the page at the same time: keep to the analysis (`app/analysis/core.py`,
`engine.py`, `events.py` where needed).

Done: one pass over the histories on the real case, the same page figures as two passes (or within the stated bin
resolution for percentiles), and the measured time per history before and after.
