# 002-8: the notes, the judgment default, the holders' acts and the listing, compiled for one draw

The product is moving to an exact evaluator (`design/002-exact-evaluator.md`; read it whole, especially "The frame"
and "Port order"): the whole tree of what can happen in the lawsuit, walked one operating draw at a time, depth
first, in numba, with the state saved and restored at each decision. It is how the page's figures become exact
instead of sampled, on a laptop in under an hour. Today's Python (`app/analysis/events.py`, `events.Chain`) is the
definition while both exist; each area is ported against it and must agree with it exactly, on every draw, every
field. This is port order 6.

What exists to build on (read each):
- `app/exact/fields.py`: where each part of one draw's state lives (scalars `S`, per-day `D` and `P` arrays); each
  area owns a block (yours: scalars from `S_NOTES`, per-day int64 from `D_NOTES`).
- `app/exact/core.py`: the chain's core for one draw, already identical to the Python: the judgment's timeline, the
  amount owed (`owed_at`), `live`, `mark`, and the bookings `pay`, `petition` (which returns whether it is now the
  petition: where the Python then rebooks the at-the-market sales, call `equity.atm_rebook`) and `resolve`.
- `app/exact/equity.py` (with `fields_equity.py`, `export_equity.py`): the company's equity, identical to the Python,
  including `coupon_rebook`, the coupon priced off the share price, which reads a coupon table whose columns
  `fields_equity.py` defines (`C_*`) and which it says your area owns.
- `app/exact/export.py`: a Python Chain's core state on one draw in that layout.
- `app/exact/oracle.py`: random complete histories of the real case (`style="long"` reaches levies, defaults,
  acceleration, petitions, delisting) and the Python's reference.
- `tests/test_exact_equity.py` and `tests/test_exact_bookings.py`: how a port is checked: hook the Python method at
  its boundary inside real histories, export the state just before it, run the compiled function on that state,
  and compare with the Python's state just after; and compare the compiled accessors with the Python's after every
  `Chain.step`, on every draw at many days.

Your area: the convertible notes and the listing as `events.Chain` books and reads them (QUESTIONS_20240514 §§2.1,
2.3, 3.1–3.3, 4.6): the judgment default (`judgment_default`, `_default_at_ruling`, `book_default`,
`default_available_day`), the judgment's standing (`standing_amount`, `judgment_amount_entered`,
`judgment_standing`: its states as integer codes), the holders' acts and routes (`holder_route_days`,
`holder_route_days_path`, the notes falling due with how they fell due: `mark` for `notes_due` and
`notes_due_how`), the coupons (`instrument_cash`, `coupon_cash_cents`, `coupon_when_due`; the priced coupon's
rebooking is equity's `coupon_rebook`, on your table), the listing (`listing_dates`, `listing_step`,
`repurchase_day`), and the `Chain.step` and `decide_distress` branches that book in this area (`judgment_default`,
`notes_due_date`, `listing_date`/`listing`, `nonpayment`). Read every one of them, and what they call, whole, before
writing anything.

Write `app/exact/fields_notes.py` (your block's fields and tables, each naming the Python it holds),
`app/exact/notes.py` (the compiled functions, one per Python method, each reproducing it on one draw),
`app/exact/export_notes.py` (the Python Chain's notes state on one draw in your layout) and
`tests/test_exact_notes.py`. Calendar arithmetic (business days, trading days, the listing and repurchase dates)
is computed in Python once into tables the compiled functions read, as `core.entry_days` and `export_equity` do; the
compiled walk never builds dates or strings. Where the Python keeps a list, hold it in a fixed-capacity table with
its count in your scalars, and say the capacity you chose and why this case cannot exceed it.

Cash: some of these read the company's cash or the daily processor's results (`nonpayment_day`, `nonpayment_terms`,
the cash a response or the holders' route reads). Do not port the processor or the cash reads: take what they read
as values passed in by the caller. In your tests the caller passes the Python Chain's own; in the evaluator the
coordinator's cash reads over the compiled line will. `tau` and `cash_out` are the next area's, not yours.

What must hold, on random real histories (`oracle.histories`, both styles, several seeds, on a few draws): after
every step of every history, each compiled accessor equals the Python's on every draw at many days; and every
booking in your area, run compiled on the state exported just before it, gives exactly the Python's state just
after it on your fields, the core's fields it writes (marks, petition and its cause, the obligations' incurred
days) and the event cash. Some core fields (`stayed_from`, `lock_amount`, `lock_day`) are computed by the Python from
the whole state whenever they are read, so any booking moves them; they are the stays' port's to compare, not yours.
Report what you checked (histories, steps, draws, accessor reads, bookings by kind), the capacities and why they
hold, and anything in the Python that a per-draw state cannot hold.

Keep to your new files; do not change `events.py`, `core.py`, `fields.py`, `export.py` or the equity files (the
coordinator is changing the core at the same time). If you need something from the core that is not there, say so
