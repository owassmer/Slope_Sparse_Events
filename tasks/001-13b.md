# 001-13b: pool the walk at its real size

The full-tree walk will end with about 5.4M joint histories (an estimate with a heavy tail; about 2.9M are walked so
far), in about 4,000 pieces spread over 15 or more waves. Pooling (`slope pool-tree`, `app/analysis/tree_pool.py`) is
what turns those pieces into the tree the rest of the product reads: every question and the histories that reach it,
and the coverage and arithmetic gates that show the tree is whole. Nothing downstream (the judgment model's answers,
the cash distribution, the page) can start until the pool is done, so how long pooling takes is now the walk's tail.

Two things stand between the pool as written and the walk as it is:
- **Where the pieces are.** GitHub waves now upload each job's small files (`piece.json`, `next.txt`) as artifact
  `out-N` and its events (`events.pkl.gz`) as `heavy-N`; pool-tree downloads `heavy-N` alone and finds no `piece.json`,
  so it fails on every GitHub wave (seen on walk-f7's run 37863838808). Pieces walked on the AWS host are whole
  directories (`piece.json`, `next.txt` and the events together) synced from S3 into a local folder holding many
  pieces. The pool must take both, every piece exactly once.
- **How long it takes.** It runs as one process: each piece is read, every history pickled into SQLite with its
  question references, then one pass over all histories exports the gates. At 5.4M histories that may be many hours
  on one core. It will run on the AWS host (128 cores, 246 GB memory, a large disk; no 20-minute limit there). It has to
  be fast for a reason beyond waiting: a pool is not run once. Any fix to the walk or the question rules means pooling
  again, and the host costs money by the hour, so a pool that takes hours makes every correction slow and expensive. Make it use the host: ingestion of pieces is independent, and the
  export's per-history accumulation adds up, so both can be split and combined, provided the result is identical to a
  single-process pool (same coverage verdict, same masses, same question set).

What a correct pool is does not change: every piece's histories and draw counts must match its `piece.json`, a piece
never counts twice, coverage is judged by input routes, and a duplicate or truncated piece still stops it.

Measure before and after on real pieces: `var/remote/walk-f*/` and `var/remote/walk-f*.aws/` hold the small files of
every wave so far, and you can build realistic test pieces with `slope walk-tree` on a small partition. Report the
measured ingestion and export rates per history and the projected time and disk for 5.4M histories on 128 cores.

Done: pool-tree accepts GitHub runs with split artifacts and local folders of whole pieces; on 128 cores the projected
pool of the full walk takes well under an hour; a multi-process pool gives the same result as a single-process pool on
the same pieces (shown by a test).
